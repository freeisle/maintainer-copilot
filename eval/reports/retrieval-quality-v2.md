## 不变条件与验收边界

原 retrieval-v2 的 24 条问题/标签未改，固定 6,349 chunk（3 仓库）未重建。原业务库只读；测试仅在 mc_test_ 数据库随机 schema 中写入。保留历史 n=8 和上轮 n=24 报告。当前 24 条是开发诊断集，不能把同集优化收益当作独立泛化证据。

模型：BGE-M3 5617a9f61b028005a4858fdac845db406aefb181，BGE-reranker-v2-m3 953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e。CPU、OMP/MKL=4、batch=4、pool=50、k=8、RRF K=60、无 LLM rewrite。报告包含完整数据集/语料哈希、数据库全行摘要、源码 SHA 和实现哈希。

## 根因及证据

- ret-004：七个目标文件中只有 IngestionEngine 和 IndexerNode 进入原始 50 候选池。前者 dense16/sparse14/fusion6，CE13（0.212987）；后者 dense3/fusion11，CE28（0.074049）。CE 优先 issue95（0.772866）、测试（0.769424）、README（0.698238）。其他五个节点不在任一完整通道池中；这是召回缺口与重排损失叠加，不是输出去重把全部节点删掉。节点级覆盖必须按 /7 报告。
- ret-007：后端 DashboardServiceImpl 在 dense38、融合联集72，原始50截断丢失；前端 dashboardService.ts 不在通道池。后端实现使用 KbHitRate/hits/citations 等英文 SQL/标识符，与中文业务措辞存在差异。前端曾因行窗主键碰撞仅保留最后一段，但 getDashboardKbHitRate 仍在该段，因此不能把这条失败完全解释为语料丢失。
- ret-014：标注文件存在但关键异常说明只在 Python 模块 docstring，原 AST 切分未索引它。固定库中该异常串仅出现在 Java 文件。旧错误提取还包含尾部中文问号，LIKE 不匹配。符号通道按词边界提取异常名与方法名，不带语言先验；即使调入 Python 调用端，也不能把文档命中当作原始异常解释已经入库。
- ret-003：VectorRetrieverService 接口不在任何通道池；实现和版本说明进入池，第一相关文档最终第4。缺失接口不能靠重排恢复。
- ret-005：DefaultIntentClassifier 已在池；IntentGuidanceService dense41/fusion73 被截断；IntentResolver 不在通道池。
- ret-006：Milvus 实现 dense10/fusion22，在池内；README 同样在池。原重排 Recall@5=1/2，Recall@8=2/2，属于截断位置上的覆盖损失。
- ret-013：Milvus 实现在池，VectorRetrieverService 接口不在任一通道池。
- ret-015：order_tools.py 在 dense14/15、sparse4/6/13/35，多块进入池；原 CE 首个相关文档第4，属于排序问题。
- ret-021：executor 已排首位，config.py 不在任一通道池。MC_DRY_RUN 运行时前缀与字段 dry_run 的映射不直接体现在常量文字中。

## 最小实现与回滚

1. 默认不变的 per-call trace：通道全部候选、dense/BM25/精确模式、RRF联集、截断/去重/CE/覆盖阶段。诊断只追加只读 fetch，不二次计算查询向量。
2. symbol_recall（默认 false）：抽取显式 camelCase/PascalCase/snake_case/路径名，以转义的字面边界匹配同仓库缓存文本，作为第四 RRF 通道。没有按 ID、完整问题、目标路径或 Java/Python 优先级的规则。
3. coverage_pool（默认 false）：在通道联集按文档优先分配相同 50 个 CE 名额，再补同文档片段。不会扩大 top_k 或 CE 池大小；可能损失同文件其他相关片段，因此必须检查负向变化。
4. rank_blend（默认 false）：文档级 fusion/CE 排名以 1/(10+rank) 等权组合，不比较不可校准的 BM25/CE 原始值；保留 CE 分和单独 ranking_score，Solver 使用后者。没有全局源码优先或测试/Issue 惩罚。
5. 修复未来入库：保留 Python 模块说明，给行窗分段唯一标识。既有方法 ID 不变。固定库未重建，旧索引的迁移/收益必须另行验证。

## 实验方法

E0：原召回+CE；E1：symbol_recall+coverage_pool；E2：rank_blend；E3：两组组合。三个开关仍可独立消融。E4 未执行，无外部 LLM 改写收益混入。

为限制内存，预计算24个查询向量后释放 Embedding 模型；后续每个实验仍实际执行 pgvector SQL。CE cache 按模型 revision、依赖、batch、查询与全文哈希存储真实分数；相同候选复用，新增候选实际推理。分别报告缓存命中/新推理数量，不把缓存耗时当成真实模型吞吐。

首次双模型试跑因主机可用内存不足1GB主动停止，未计完整指标。正式主实验分阶段 Embedding 预计算耗时82.34秒，释放前RSS约1.29GiB，释放后0.30GiB；挑战集对应70.28秒、1.87GiB、0.46GiB。这是模型驻留优化，不是修改精度/截断带来的收益。

## 仍有的限制

历史6114条复用向量缺逐行revision来源，仅3条兼容抽查不能证明全量来源一致。固定同库对照可以比较策略，不能消除历史向量溯源风险。候选池之外的节点/接口/配置仍需新的通用召回证据；不通过扩大k或修改标签掩盖。挑战集为内部6条、源码证据先验核验，与开发集可能共享文件，不能声称独立外部盲测或统计显著性。生产默认开关保持关闭，最终推荐依据完整正负结果。

## 文档级指标之外的证据审查

ret-007 dense38 的后端候选 ccee5e779dab1089 实为 loadTrends 的 part_idx=5，包含错误率/无知识率趋势，不是 loadKbHitRate 的命中率公式。即使该文件进入最终结果，也应单独检查是否包含 citationCount * 100.0 / hitCount 的实际实现，不能把文件级 Recall 当作完整答案质量。ret-004 的 IndexerNode 候选是 attachPipelineMetadata 方法，未召回节点执行主方法。ret-014 的 Java 解析函数可解释 substring(1) 的异常原因，gold 只标 Python 调用端，因此文档级未命中不等同于 Java 证据完全无关；本轮保留原标注并如实说明局限。

## 采用决策与未完成目标

本轮获得可复现的局部收益，但没有获得足够一致的整体质量提升；三个新策略保持默认关闭。E1 的 Hit@3 达到 0.8333，代价是 ret-003 的 Recall@8 从 2/3 降至 1/3；单独 symbol 没有改变最终指标，coverage 单独复现了 E1 的变化。E3 的 Hit@8 提升 0.0417、Recall@8 提升 0.0060，但 MRR 不变，ret-024 从第2降至第4，ret-023 从第1降至第2。从排名变化推断，等权融合没有辨认“入口引用”与“实现证据”的区别：main.py 获得更高融合先验，挤压 solver.py/server.py 的直接实现证据。不要以总体均值掩盖这些退化。

ret-004 在 E2/E3 仅找回第6位 IngestionEngine，7个节点只覆盖1个，不能宣称 Pipeline 追踪已解决。ret-007 和 ret-014 的最终 top-8 仍未命中。下一步应优先在隔离的新索引中验证切分修复及向量溯源，再研究中文业务概念到具体方法的通用映射；不继续对这24题调参数。Recall@5=0.8、MRR@8=0.72 和重点三题改善至少两题的挑战目标未达成。没有执行 E4，没有修改标签或引入 LLM 改写。
